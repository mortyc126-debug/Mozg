# RESULTS_LEDGER.md

Для каждого ключевого эксперимента: вопрос, конфигурация, файлы, метрики,
наблюдения, допустимый вывод, ограничения, исправленные интерпретации.

## КРИТИЧЕСКИ ВАЖНЫЕ ИСПРАВЛЕННЫЕ ОШИБКИ (читать в первую очередь)

Эти пункты стоили нескольких раундов исправлений в ходе проекта. Не
повторять.

1. **Нулевой подписанный R не означает отсутствия временного эффекта.**
   R = (сумма импульсов стимул - сумма импульсов фон) / n_узлов может
   быть строго нулевым, если импульс просто СДВИНУЛСЯ по времени (напр.
   с 35мс на 36мс), а не исчез. Обнаружено в v0.4: окно 0-50мс давало
   R=0 почти везде, что ошибочно интерпретировалось как "нет эффекта",
   пока растровая метрика changed_fraction не показала обратное.

2. **changed_fraction (доля узлов с изменённым растром) чувствительна к
   временному разрешению и имеет потолок.** Сравнение долей затронутых
   узлов между окнами РАЗНОЙ длины (например, 0-50мс vs 50-200мс)
   некорректно: более длинное окно почти всегда даёт бОльшую долю просто
   потому, что у него больше шансов хотя бы на одно совпадение изменения,
   а не потому что эффект "нарастает". Использовать только РАВНЫЕ окна
   для сравнения.

3. **Совпадение пустых растров НЕ означает совпадения внутренних
   состояний.** Показано в v0.3 recovery-протоколе: во время общего
   молчания (оба -- baseline и stimulated -- не дают импульсов) `v`,
   `adaptation`, `syn_effective` всё равно отличаются. `changed_fraction`
   в этот период равна нулю не потому что эффекта нет, а потому что
   не с чем сравнивать на уровне импульсов.

4. **Разный фон при разных весах -- допустимое явление, не ошибка.**
   При одинаковом начальном состоянии и шуме разные веса МОГУТ давать
   разные фоновые (baseline, без стимула) траектории уже внутри
   тестового окна. Это не смешение факторов, если веса зафиксированы
   один раз и не переобучаются заново для каждого тестового состояния.

5. **Собственный прогрев вариантов НЕ даёт общего начального состояния.**
   Если каждый вариант весов проходит свой собственный warm-up с тем же
   seed, состояния после прогрева всё равно РАЗНЫЕ (веса разные ->
   динамика разная). Это отдельный вопрос от "какой эффект дают веса при
   одинаковом контролируемом старте". В v0.4 использовался именно
   собственный прогрев -- см. соответствующий раздел ниже.

6. **Регулярность отдельных узлов, межузловое согласование и
   популяционный ритм -- РАЗНЫЕ свойства.** Узел может быть регулярным
   (низкий ISI CV) при этом не быть согласованным с другими узлами по
   фазе. v0.3 явно разделил эти три понятия через ISI CV отдельных
   узлов, cyclic-shift контроль (межузловое согласование) и
   автокорреляцию популяционного счётчика (ритм).

7. **Знак лага (кросс-корреляция) был перевёрнут и исправлен.** Функция
   normalized_xcorr в quantitative_recovery.py изначально имела неверный
   знак (проверено на явном примере с известными индексами событий, не
   на словесном рассуждении). Финальная, верная конвенция: положительный
   лаг = stimulated ЗАПАЗДЫВАЕТ относительно baseline. Самопроверка:
   a[30]=1, b[36]=1 => best_lag(a,b) = +6, best_lag(b,a) = -6,
   best_lag(a,a) = 0.

8. **Условная occupancy по непустым окнам НЕ сравнима напрямую с
   безусловной rate * bin_duration.** В v0.3 обнаружена ошибка: индекс
   "coactivation" усреднял долю активных узлов ТОЛЬКО по окнам, где хотя
   бы один узел уже активен (условное среднее), а сравнивался с
   безусловным rate*bin_s. Верная формула, гарантирующая occupancy <=
   rate*bin_duration: усреднять occupancy по ВСЕМ окнам без фильтрации.

9. **p = (1 + число контрольных значений >= наблюдаемого) / (B + 1);**
   при B=100 минимальная достижимая оценка 1/101 ~ 0.0099, НЕ ноль.
   "Перцентиль 100%" не означает абсолютную уверенность.

10. **Шумовые повторы НЕ являются независимыми структурами.** "3 шума
    одной сети" != "3 независимые сети". Используется терминология
    development_seed (структура) отдельно от noise_seed/state_seed/
    test_seed (реализации шума при ФИКСИРОВАННОЙ структуре).

11. **Взаимодействие числа контактов в версии 0.5 равно +120 для
    seed=11: это ВЫРАЖЕННАЯ неаддитивность, а не её отсутствие.**
    I = M_совместное - M_бюджет - M_длина + M_исходное
      = 588 - 828 - 592 + 952 = +120.
    Малый дополнительный эффект бюджета ПРИ УЖЕ включённом штрафе длины
    (штраф длины сокращает контакты на 360, добавление бюджета поверх
    штрафа -- ещё лишь на 4) -- это свидетельство того, что штраф длины
    делает бюджет почти неактуальным (сеть и так разрежена), а НЕ что
    бюджет "не работает".

12. **Одинаковая частота при включённом гомеостазе сама по себе НЕ
    доказывает компенсацию всех структурных различий.** normalization_
    events=0 подтверждает лишь, что ограничитель суммы весов не
    вмешивался. Пороговый гомеостаз мог компенсировать разницу связности,
    а мог оказаться неважным, если сетевой вклад в этом режиме и так мал
    относительно drive. Роль гомеостаза отдельно НЕ изолирована.

13. **Устойчивый по знаку функциональный эффект (v0.5, F_200) НЕ
    равносилен изолированному эффекту топологии.** Штраф длины меняет
    ОДНОВРЕМЕННО число контактов, их среднюю длину И скорость роста
    (см. пункт про замедление роста в v0.5 структурном аудите). Снижение
    F_200 при штрафе длины показано КАК СОВОКУПНОЕ последствие этой связки,
    не как эффект топологии при уравненной плотности. Это повторяющийся
    паттерн проекта (см. также ограничение v0.4 про 39/80 незатронутых
    узлов) -- согласованность знака на нескольких геометриях/направлениях
    подтверждает воспроизводимость наблюдения, но не автоматически
    вычленяет причинный механизм. ЧАСТИЧНО РАЗРЕШЕНО в v0.6 для условий
    БЕЗ бюджета (продление роста показало: различие исчезает вместе со
    сближением графов, значит было в основном задержкой) -- но НЕ для
    условий С бюджетом, где структурное различие устойчиво, а
    функциональное направление всё равно не сохраняется.

14. **np.isclose с ненулевым atol/rtol НЕ является точной проверкой,
    даже при "очень маленьком" допуске.** В ходе разработки v0.6
    первая версия verify_snapshot_matches_v05() использовала np.isclose
    с atol=1e-12 для сравнения метрик (rate_hz и др.), что было
    ОШИБОЧНО названо "точным совпадением". Для НЕИЗМЕНЯЕМЫХ числовых
    величин, полученных ДЕТЕРМИНИРОВАННЫМ путём (тот же код, тот же
    seed, тот же порядок операций с плавающей точкой), корректная
    проверка -- точное равенство (`==` для скаляров, `np.array_equal`
    для массивов, БЕЗ параметров tolerance). Обнаружено и исправлено ДО
    полного запуска 12 траекторий -- после исправления все проверки
    также прошли точно (значения оказались буквально идентичны, допуск
    маскировал это, а не был необходим).

15. **Разные политики/условия, использующие "тот же" генератор
    случайных чисел для НЕСКОЛЬКИХ разных целей (выбор получателя +
    выбор источника внутри события), могут незаметно РАСХОДИТЬСЯ по
    потреблению случайных чисел, даже если предполагается общее
    расписание.** В v0.7 первая версия run_rewiring_trajectory()
    использовала ОДИН rng для выбора получателя (pick_receiver) И для
    выбора old_source/new_source (do_rewire_event) -- у "weakest"
    число вызовов rng.choice() внутри события МЕНЬШЕ, чем у "random"
    при отсутствии ничьей по минимальному весу (один choice меньше),
    поэтому уже после первого события состояние генератора для
    следующего pick_receiver() расходилось между политиками, хотя
    планировалось общее расписание. Обнаружено эмпирически (сравнение
    списков receivers между policy напрямую), не по теоретическому
    рассуждению. Исправлено разделением на независимые генераторы:
    один для расписания (общий поток), другой для внутренних выборов
    события (свой на политику, не влияет на общий поток). Урок:
    "используем тот же seed" НЕ гарантирует "используем ту же
    последовательность чисел для данной подцели", если генератор
    расходуется на разное количество операций в разных ветвях кода --
    нужно либо разделять генераторы по роли, либо строить расписание
    заранее одним вызовом (что и было сделано дополнительно в v0.7,
    build_fixed_schedule, как более сильная гарантия).

16. **"Средний разброс внутри групп" (среднее std по группам) НЕ является
    корректным разложением общей дисперсии на внутригрупповую и
    межгрупповую компоненты -- нужно использовать точное разложение
    через суммы квадратов, и отношение "внутригрупповая/общая" считать
    через ДИСПЕРСИИ (квадраты std), а не через сами std напрямую.**
    Первая версия сводки v0.7 сравнивала std напрямую (0.035 против
    0.038) и получила ошибочную оценку "~93%"; при пересчёте по формуле
    (total_variance = within_variance + between_variance, все через
    np.mean((x-mean)**2) с весом по размеру группы) доля внутригрупповой
    дисперсии оказалась 90-98% в зависимости от пары политик -- ЧИСЛЕННО
    БЛИЗКО к прежней ошибочной оценке, но полученной корректным методом
    (см. RESULTS_LEDGER.md v0.7 для точных чисел по каждой паре).
    Дополнительно: утверждение "эффект того же порядка, что и SEM" было
    убрано -- SEM с учётом вложенности (повторы внутри структуры,
    структуры не независимы) не был по-настоящему посчитан; "разброс
    между 6 группами" был ошибочно назван SEM. Урок: любое утверждение о
    доле дисперсии или неопределённости среднего должно либо содержать
    формулу разложения явно, либо не выдвигаться как количественная
    оценка -- качественное "разброс велик относительно эффекта" не
    требует спорной статистики, а точное число требует точного метода.

17. **При совмещении двух независимых источников событий на одной
    сетке времени (естественная активность + принудительная
    стимуляция) НЕЛЬЗЯ обрабатывать их как последовательные отдельные
    пакеты, если между ними есть общий побочный эффект (здесь --
    STDP, использующий текущие trace).** Первая реализация v08_
    experience_rewiring.py делала electrical_step (естественная
    активность, включая STDP/передачу/сброс) ЗАВЕРШЁННЫМ шагом, а
    ЗАТЕМ отдельно force_spikes (тоже с собственным вызовом STDP) для
    принудительной стимуляции того же временного шага. Последствия:
    (а) если один и тот же узел оказывался и в natural_fired, и в
    forced-списке на одном шаге -- он получал СТДП-обновление,
    передачу, сброс адаптации/рефрактерности/trace ДВАЖДЫ; (б) даже
    для РАЗНЫХ узлов на одном шаге второй вызов STDP видел уже
    обновлённый (первым вызовом) trace, создавая искусственное
    отношение "раньше/позже" внутри одной номинально одновременной
    отметки времени. ИСПРАВЛЕНО: явное разделение шага на (1) интеграция
    электрической динамики БЕЗ немедленной STDP/передачи/сброса ->
    natural_fired, (2) определение forced_fired по расписанию, (3)
    объединение fired = natural_fired | forced_fired, (4) ОДИН
    вызов STDP/передачи/сброса на объединённую маску, использующий
    trace ДО этого пакета для ВСЕХ узлов маски одновременно. Проверено
    4 искусственно СКОНСТРУИРОВАННЫМИ (не случайно совпавшими в
    симуляции) unit-тестами: один узел natural+forced не даёт двойного
    учёта; два разных узла (один natural, один forced) обрабатываются
    без искусственного порядка; импульс и перестройка на одной отметке
    -- текущая передача идёт по старому графу, новый контакт активен
    только со следующего шага; при выключенной пластичности веса
    НАСТОЯЩИ статичны, включая экстремальные (провоцирующие clip/
    нормировку) значения. Урок: "редкое совпадение" в стохастической
    симуляции -- недостаточное основание считать код корректным без
    целевых тестов; на полном 24с прогоне такое совпадение произошло
    12 раз только для перестройка+стимул и было бы возможным источником
    систематической (не случайной) ошибки во ВСЕХ 72 траекториях, если
    бы осталось неисправленным -- т.к. расписание стимуляции и
    перестройки детерминированы и совпадения повторяются идентично при
    каждом запуске с теми же параметрами.

18. **Случайная потеря файла результатов в ходе организационной работы
    (не связанной с самим экспериментом) -- отдельный класс риска,
    требующий явной, а не подразумеваемой оговорки о происхождении
    данных.** В ходе наведения порядка в директориях (после завершения
    полного прогона v0.8) неаккуратная команда очистки удалила
    `v08_experience_full.pkl` ДО того, как для него был посчитан
    независимый контрольный хеш. Файл восстановлен повторным запуском
    того же детерминированного кода с теми же параметрами; все
    ОПУБЛИКОВАННЫЕ числовые результаты (полная таблица C/C_A/C_B, 24/24
    структурных контроля) при этом воспроизвелись точно. Но это
    подтверждает воспроизводимость КОДА, а не побайтовую идентичность
    УТРАЧЕННОГО файла -- хеш оригинала не был сохранён заранее, поэтому
    строго говорить можно только о том, что "данные повторно
    сгенерированы; опубликованные показатели воспроизведены точно,
    контроли пройдены", а не о том, что "восстановленный файл идентичен
    утраченному". Урок: SHA-256 для файлов результатов стоит фиксировать
    СРАЗУ после генерации (до любых последующих файловых операций), а
    не только на этапе финальной сборки релиза -- иначе окно между
    "файл создан" и "файл заманифестирован" остаётся неконтролируемым.

19. **Перестановочный нуль, воспроизводящий проверяемый эффект, --
    не нуль, а сломанный тест. Центрированность нуля обязана
    проверяться явно, а не предполагаться.** В v0.11 первая версия
    проверки (v11_verify.py::V3) переставляла, какие ТЕСТОВЫЕ ШУМЫ
    усредняются для каждой ветви, но не трогала приписку самих ВЕТВЕЙ.
    Структура "несовпадающая минус совпадающая" сохранялась внутри
    перестановки, поэтому нулевое распределение дало среднее +1.6085
    при наблюдённом эффекте +1.6097 -- то есть "нуль" содержал эффект
    целиком, и тест не проверял проверяемую гипотезу вообще. Первая
    версия давала p=0.48, что при поверхностном чтении выглядело бы
    как "эффекта нет", а после исправления p=0.0001 -- то есть ошибка
    могла увести вывод в ЛЮБУЮ сторону, а не только в одну.
    Обнаружено по совпадению среднего нуля с наблюдением. ИСПРАВЛЕНО:
    для ПАРНЫХ данных (один и тот же шум подан обеим ветвям) верный
    нуль -- случайный переворот ЗНАКА разности по каждому шуму
    (v11_verify2.py). Урок: в любой перестановочный тест встраивать
    обязательную самопроверку "среднее нуля ~ 0"; перестановка должна
    разрушать именно ту связь, которая проверяется, и это надо
    показывать численно, а не обосновывать словами.

20. **Признаки декодера, содержащие сам артефакт стимуляции, делают
    задачу тривиальной, а не решённой. Потолок точности НА КОНТРОЛЕ --
    признак дефекта задачи, а не успеха.** В v0.11 фазе 2 первая версия
    задачи "распознать предъявленный порядок" брала признаки с ВСЕЙ
    сети начиная с момента предъявления. Принудительные импульсы
    пишутся в растр наравне с естественными, поэтому "кто сработал на
    отметке t0" было ПРЯМОЙ меткой класса: декодер читал не отклик
    сети, а сам факт подачи стимула. Точность вышла 1.0000 на ВСЕХ
    36 комбинациях И на контроле M3 (без пластичности), при этом
    контроль перемешанных меток честно дал 0.49 -- то есть утечки в
    перекрёстной проверке не было, задача просто не требовала сети.
    Обнаружено по совпадению потолка на M1 и на M3: если необученный
    контроль решает задачу идеально, задача не про обучение.
    ИСПРАВЛЕНО: признаки берутся только с НЕ стимулированных узлов и
    строго ПОСЛЕ обоих принудительных импульсов
    (FEATURE_START_MS = t0 + lag + 1). Дефектный вариант сохранён в
    коде и считается параллельно -- ради документирования причины, не
    как результат. Урок: контроль нужен не только на утечку метода
    (перемешанные метки), но и на тривиальность самой задачи -- эти два
    контроля ловят РАЗНЫЕ дефекты, и второй требует, чтобы необученный
    контроль решал задачу ХУЖЕ обученной сети.

21. **Регрессия с точкой-якорем, создаваемой самим определением
    величины, даёт положительный наклон при ПОЛНОМ отсутствии связи.**
    В v0.12 первая проверка пространственного распространения
    (v11_waves.py) считала наклон регрессии "время первого импульса" на
    "расстояние от начала волны". Начало волны определяется как САМЫЙ
    РАННИЙ узел, поэтому у него d=0 И t=0 ПО ПОСТРОЕНИЮ. Эта точка --
    якорь в левом нижнем углу облака, и прямая наименьших квадратов
    через облако плюс якорь имеет наклон ~ (среднее t / среднее d)
    независимо от наличия связи. Численно: на ПЕРЕСТАВЛЕННЫХ координатах
    наклон вышел +9.53 против +10.24 на реальных -- то есть 93% эффекта
    было артефактом. Без контроля перестановки был бы объявлен вывод
    "распространение подтверждено, наклон +10.2, положителен в 1022 из
    1287 всплесков" -- полностью ложный.
    ИСПРАВЛЕНО (v11_waves2.py): узлы-начало исключены из регрессии,
    вместо наклона используется ранговая корреляция (не зависит от
    масштабов и не тянется одной точкой). После исправления контроль
    дал -0.0014 (обязан быть ~0), и эффект исчез: разность
    реальный-контроль +0.0153 при отношении к собственному разбросу
    0.060.
    Урок: если величина ОПРЕДЕЛЕНА через экстремум выборки (самый
    ранний, самый сильный, ближайший), проверь, не создаёт ли это
    определение точку, которая тянет оценку. Контроль, сохраняющий ВСЁ
    кроме проверяемого признака (здесь -- те же импульсы, переставленные
    координаты), ловит это; отсутствие такого контроля -- не ловит.

22. **Вмешательство, стираемое внутри шага, даёт ТОЧНЫЙ ноль -- и ноль
    читается как "эффекта нет", хотя эксперимента не было.** В движке
    проверялось, задаёт ли ориентация агентов q сторону изгиба пласта.
    Ветка с разворотом q на 180 градусов вышла ПОБИТОВО равной ветке
    без вмешательства: 0 переворотов знака из 12, cos(q_B, q_A) = 1.000,
    коэффициенты прогиба совпали до последней значащей цифры. Причина:
    подмена делалась после возврата из step(), а внутри шага порядок
    updateOrientation -> физика, и при align = 0 (значение по умолчанию)
    updateOrientation не обновляет ориентацию, а ПЕРЕЗАПИСЫВАЕТ её
    локальной асимметрией, c.qx = c.ax. Подставленное значение стиралось
    до того, как его кто-либо прочитает.
    Поймано по ТОЧНОСТИ совпадения: настоящий нулевой эффект в
    многошаговой нелинейной системе даёт близкие, но не побитово равные
    числа. Побитовое равенство двух веток, которые обязаны были
    разойтись, -- признак неработающего инструмента, а не результата.
    ИСПРАВЛЕНО: в движок добавлена точка вмешательства между обновлением
    ориентации и физикой (при незаданном значении не делает ничего;
    побитовое тождество с нетронутым движком подтверждено на 6 сверках),
    подмена стала удерживаемой и применяется каждый шаг. После этого
    ветки разошлись, и ответ получился содержательный: разворот q
    удваивает ВЕЛИЧИНУ прогиба, поворот на 90 градусов уменьшает её
    вдвое, но СТОРОНУ не переворачивает (5 из 12 при объявленном пороге
    10 из 12).
    Урок: в любой проверке вмешательством сначала показать, что
    вмешательство вообще состоялось -- что ветки разошлись. Отдельной
    строкой в выводе, до обсуждения эффекта. И знать порядок вызовов
    внутри шага: подмена, сделанная снаружи шага, может быть стёрта
    первым же его действием.

23. **Правило чтения для ОТРИЦАТЕЛЬНОГО исхода было записано как
    "ничего не изменится", хотя верное предсказание -- "станет
    случайным".** Там же объявлялось: если q задаёт сторону, знак
    перевернётся не менее чем на 10 сидах из 12; если не задаёт -- не
    более чем на 2. Вторая половина неверна: при сильном возмущении
    отсутствие управления знаком даёт знак СЛУЧАЙНЫЙ, около 6 из 12, а
    не сохранённый. Полученные 5 из 12 -- ровно этот случай -- попали в
    объявленную "неопределённую" полосу и формально не читались, хотя
    содержательно они и есть отрицательный ответ.
    Отрицательная половина вывода уцелела только потому, что порог для
    ПОЛОЖИТЕЛЬНОГО утверждения (не менее 10 из 12) был сформулирован
    правильно и не выполнен.
    Урок: предрегистрируя правило чтения, для КАЖДОГО исхода записывать
    не словесное отрицание гипотезы, а численное предсказание меры при
    этом исходе. "Эффекта нет" и "мера сохранится" -- разные вещи;
    какая именно ожидается, зависит от силы возмущения, и это надо
    продумать до запуска, а не после.

24. **Результат объяснён механизмом, код которого в этой конфигурации
    НЕ ВЫПОЛНЯЛСЯ, и подтверждающий тест проверял тот же неисполнявшийся
    путь.** Направление изгиба слоя объяснялось через bodyRadii --
    функцию, делающую одну точку агента крупнее другой, "биметалл гнётся
    к тонкой стороне". Объяснение было подкреплено сконструированным
    тестом из 8 проверок, и тест верен. Но bodyRadii вызывается только
    из physicsTwoPoint, то есть при twoPoint = true, а НИ ОДИН прогон со
    слоем этого параметра не задавал: по умолчанию он false. Проверено
    прямо -- у агента в этих прогонах вторая точка вырождена, p1 и p2
    совпадают до последнего разряда, формы у него нет. Работала другая
    вещь: модуляция равновесного расстояния в physicsPoint,
    de = D0*(1 - 0.5*k*(n*q)).
    Сконструированный тест не спас: он проверял, что механизм РАБОТАЕТ
    ТАК, но не проверял, что он в этом опыте ВООБЩЕ ВКЛЮЧЁН. Эти два
    вопроса разные, и второй не задавался.
    Обнаружено косвенно -- при разборе, почему вмешательство в ориентацию
    не переворачивает сторону изгиба. Ответ оказался прост: механизм, для
    которого переворот обязан был сработать, не действовал.
    Урок: прежде чем объяснять результат устройством механизма, вывести
    в лог, что путь этого механизма в данной конфигурации исполняется --
    флаг режима, число вызовов, любое прямое свидетельство. Параметр по
    умолчанию выключен -- нормальное положение дел; опасно то, что
    объяснение при этом читается связно и тестом подтверждается.

25. **Сила вмешательства выбрана в единицах НЕ ТОЙ величины, из-за чего
    положительный контроль не мог пройти в принципе.** Проверялось,
    наследуется ли сторона прогиба от кривизны стартового ряда. Ряду
    навязывалась дуга обоих знаков, амплитуды брались в долях
    собственного джиттера ряда (+-0.2): 0.1, 0.4 и 1.6 как заведомо
    подавляющая. Но джиттер -- СМЕЩЕНИЕ, а проверяемая величина --
    КРИВИЗНА. При полуразмахе ряда 195 стрелка 1.6 отвечает коэффициенту
    4.2e-5, тогда как процесс сам производит 1.0e-3: "заведомо
    подавляющее" вмешательство было в 24 раза СЛАБЕЕ проверяемого
    явления.
    Ошибка не превратилась в ложный вывод только потому, что
    положительный контроль был объявлен заранее и провалился: все три
    амплитуды дали 0 из 24 и побитово одинаковую картину по сидам. По
    объявленному правилу прогон был признан нечитаемым. Без этого
    контроля результат читался бы как "сторона от начальной формы не
    наследуется" -- вывод, который случайно оказался верен, но был бы
    получен ни на чём.
    ИСПРАВЛЕНО: амплитуды переведены в единицы КОНЕЧНОЙ стрелки (38):
    A = 4, 40 и 120. Контроль при A = 120 прошёл -- 24 из 24, ряд цел,
    -- и только после этого отрицательный результат при A = 4 (0 из 24)
    стало можно читать.
    Урок: величину вмешательства выражать в единицах ТОЙ ЖЕ меры,
    которой читается результат, и сверять её с масштабом самого явления
    ЧИСЛОМ, а не словом "заведомо больше". И держать положительный
    контроль обязательным: отрицательный результат не читается, пока не
    показано, что вмешательство вообще способно победить.

26. **Малая ВЕЛИЧИНА признака в момент съёма не означает, что исход ещё
    не РЕШЁН.** Проверялось, не циркулярно ли предсказание стороны
    прогиба по ориентации q: изогнутый пласт сам создаёт асимметрию, к
    которой q тянется. Правило было объявлено заранее и выглядело
    строгим: опора считается предшествующей, только если найдётся точка,
    где прогиб не больше 10% от конечного И снятый там q предсказывает
    конечный знак. Точка нашлась -- шаг 50, прогиб 4.2% от конечного,
    предсказание 12 из 12, -- и это было прочитано как "циркулярности
    нет".
    Прочтение слишком щедрое. Отдельная проба на необратимость (изъятие
    одного случайного числа на шаге T, то есть другая реализация шума
    при той же истории) показала, что сторона фиксируется к 25-му шагу
    из 1400, а к 50-му переворачивается уже лишь на 1 сиде из 24. То
    есть на шаге 50 q предсказывал не потому, что задавал сторону, а
    потому, что читал уже принятое решение. Независимо то же показало
    вмешательство в сам q: разворот сторону не переворачивает.
    Урок: предшествование проверять НЕОБРАТИМОСТЬЮ, а не величиной.
    Вопрос "мало ли ещё это следствие" и вопрос "можно ли ещё изменить
    исход" -- разные, и второй строже. Дешёвая проба на необратимость:
    подменить шум начиная с шага T, сохранив историю до T, и посмотреть,
    меняется ли конечный результат.

27. **Доля, измеренная на 12-24 сидах, завышена: 21 из 23 превратились
    в 42 из 65 при том же измерении и втрое большем числе сидов.**
    Проверялось, следует ли сторона прогиба за внешним полем после того,
    как ткань научена его читать. На исходных 24 сидах вышло 21 из 23
    (0.91) -- результат, который сам по себе читался бы как найденный
    источник направления. На 72 сидах та же мера дала 42 из 65 (0.65),
    контроли при этом остались на случайном уровне, то есть эффект
    настоящий, но втрое слабее первой оценки.
    Это касается не одного прогона. Вся линия про направление шла на
    12-24 сидах: 10 из 12 с p = 0.019, 11 из 12, 12 из 12. Одна такая
    доля перепроверена на 72 сидах и устояла (58 из 72), но устояла она
    ПОТОМУ, что была настоящей, а не потому, что 12 сидов достаточно.
    При 23 сидах доверительный интервал для 0.91 есть [0.72, 0.99] --
    порог 0.83 лежит ВНУТРИ него, то есть вопрос не был решён и тогда.
    Урок: если прогон стоит секунды, брать столько сидов, чтобы
    доверительный интервал НЕ НАКРЫВАЛ объявленный порог, и сообщать
    интервал, а не только счёт. Дешевизна прогона -- не повод
    останавливаться на 12 сидах, а ровно наоборот.

## v0.1: базовая модель, causal transmission, memory of order

**Вопрос:** передают ли связи причинное воздействие; записывает ли
STDP-подобное правило порядок событий A->B vs B->A в направленные веса;
проявляется ли этот след функционально (на выходных импульсах)?

**Конфигурация:** sim_core.py::simulate(), 3 независимые структуры
(seed 11/22/33), контроль transmission=False для проверки отсутствия
эффекта без связей.

**Файлы:** probe.py, probe_output.png, sequence_test.py, trace_diag.py,
trace_diag_output.png, corrected_protocol.py, corrected_protocol_output.
png, resolution_check.py, resolution_check_output.png, spike_timing.py,
raw_audit.py.

**Метрики:** дельта синаптического тока/потенциала за первые 20мс после
воздействия (Δsyn, Δv); подписанное число импульсов за 80мс; доля
пробных запусков с изменённым временным ответом; величина сдвига спайка
в мс.

**Наблюдения:**
- Контроль transmission=False дал СТРОГИЙ ноль во всех проверках --
  подтверждена причинная роль связей.
- Порядок обучения (A перед B vs B перед A) детерминированно и
  устойчиво (15/15 комбинаций сеть x состояние x направление)
  разводит знак Δsyn: положительный для A->B при обучении AB,
  отрицательный при обучении BA (и наоборот). Устойчиво к измельчению
  dt (1.0/0.5/0.25мс), величина сходится (~5-6% разброс).
- Функциональный след на импульсах: редкие (доля 2/10 - 100% испытаний
  в зависимости от dt) сдвиги спайка на 1мс (при dt=1мс) или несколько
  мс (при более мелком dt), направление сдвига статистически устойчиво
  в одну сторону (~80% испытаний "AB раньше BA") на всех трёх dt.

**Допустимый вывод:** в этой модели связи причинно передают воздействие;
порядок обучения устойчиво записывается в направленные веса и
проявляется в синаптическом токе/потенциале; функциональный эффект на
выходных импульсах реален (не численный артефакт одного шага дискретизации,
проверено при трёх dt), но мал по величине и статистически шумен на
уровне отдельного события.

**Ограничения:** 3 независимые структуры, но каждая проверена в
основном на одном/малом числе состояний памяти. Специфичность к
конкретному набору узлов (A vs B vs произвольные группы) отдельно
проверялась (specificity_test.py) и НЕ была подтверждена -- знаки S_A/S_B
разнонаправленны на всех 3 сетях. Это отдельный (отрицательный) результат
от результата про запись ПОРЯДКА (A->B vs B->A), который подтверждён.

## v0.7: структурная пластичность -- оборот (удаление+замена) контактов после заполнения бюджета

**Вопрос:** позволяет ли ограниченная замена контактов изменять уже
заполненную структуру, не разрушая её работоспособность? При одинаковой
входящей степени и суммарном входном весе даёт ли критерий удаления
другой ход структурной перестройки и динамики, чем случайный оборот
контактов?

**Файлы:** v07_rewiring.py (eligible_mask, build_fixed_schedule,
pick_receiver, do_rewire_event, run_rewiring_trajectory,
verify_invariants), v07_pilot.py, v07_full_run.py, v07_functional_pilot.py,
v07_functional_full.py, v07_rewiring_full.pkl (~72 МБ, 36 траекторий),
v07_functional_full_324.pkl (~10 МБ, 324 пары).

**Метод:** впервые в проекте реализовано УДАЛЕНИЕ контактов (до этого,
v0.1-v0.6, контакты только накапливались). Три политики на 6 исходных
структурах (3 геометрии x 2 истории роста "Только бюджет"/"Совместное",
снимки t=96с из v06_extended_growth_full.pkl):
  "none"    -- контроль, контакты не меняются (48 "контрольных отметок
              без вмешательства" на траекторию -- ПЕРЕИМЕНОВАНО из
              первоначального "пропуски", т.к. это не отсутствие
              кандидатов, а сама политика запрещает замену)
  "random"  -- получатель теряет случайно выбранный входящий контакт
  "weakest" -- получатель теряет входящий контакт с минимальным текущим
              весом (при равенстве -- случайно среди минимальных)
Новый источник в ОБЕИХ политиках перестройки выбирается ОДИНАКОВО --
равномерно из геометрически допустимых ОТСУТСТВУЮЩИХ (до удаления)
источников. Вес переносится: W[receiver,old]->W[receiver,new], старая
ячейка обнуляется -- сохраняет сумму входных весов и степень получателя.

**Ключевые технические решения, проверенные ДО полного запуска:**
- Кандидаты на новый источник фиксируются ДО удаления старого контакта
  (иначе старый источник немедленно попадает в "свободные" и часть
  замен была бы фиктивной) -- проверено явно: old_source никогда не
  равен new_source среди применённых событий.
- Расписание получателей строится ОДИН РАЗ из СТАРТОВОГО списка
  допустимых получателей (build_fixed_schedule), а не пересчитывается
  на каждом шаге -- обосновано тем, что n_candidates_i = n_eligible_i -
  in_degree_i постоянно при сохранении степени на фиксированной
  геометрии, значит множество допустимых получателей НЕ меняется от
  события к событию. Идентично для всех трёх политик при одном
  rewire_seed (проверено явно: receivers_random == receivers_weakest ==
  receivers_none на пилоте).
- ОБНАРУЖЕНА И ИСПРАВЛЕНА в ходе разработки: первая версия использовала
  ОДИН генератор для выбора получателя И для выбора old_source/new_source
  внутри события -- разное число "расходуемых" случайных чисел между
  политиками (weakest не всегда требует выбора при отсутствии ничьей)
  расходило расписание получателей уже после первого события. Исправлено
  разделением на rng_schedule (общий) и rng_event_choice (свой на
  политику, не влияющий на общий поток).
- Проверка сохранения суммы весов уточнена: точная (`==`) проверка
  невозможна из-за ошибки округления IEEE 754 при пересуммировании
  float64 в разных позициях массива (~1e-17 на наблюдаемых значениях,
  не логическая ошибка) -- используется допуск tol=1e-12. БОЛЕЕ СИЛЬНАЯ
  проверка (побитово точная): мультимножество весов КАЖДОЙ СТРОКИ
  сохраняется (`np.array_equal(np.sort(W_before,axis=1),
  np.sort(W_after,axis=1))`), т.к. значения только переносятся между
  позициями, не изменяются.
- Все инварианты (сохранение степени, суммы весов, мультимножества
  весов строки, отсутствие самосвязей, неизменность незатронутых строк)
  подтверждены на пилоте И проверяются программно (assert) на каждой
  из всех 36 полных траекторий.

**Протокол:** 24с на траекторию, замена каждые 0.5с (48 возможностей),
2 ЗАРАНЕЕ ВЫБРАННЫЕ (не случайные) реализации шума+расписания на
структуру x политику (rewire_seed in {42,43}, noise_seed in {1000,1001})

## v0.10: контроль M0 -- дополнительный вклад перестройки поверх одной пластичности

**Вопрос:** меняет ли включение структурной перестройки контактов
результат обучения относительно сети, в которой изменяются только
веса, при одинаковом опыте (AB/BA)? Это совокупный эффект включения
перестройки, НЕ чистое влияние топологии -- перестройка влияет и на
дальнейшее обучение весов (доступные для STDP контакты меняются вместе
с графом).

**Файлы:** v10_no_rewiring.py (изолированное ядро, скопировано из
v08_experience_rewiring.py БЕЗ изменения зафиксированного v0.8 кода;
единственное содержательное отличие -- rewire_policy="none" обрабатывает
отметку перестройки как "событие без вмешательства": расписание
получателей потребляется, чтобы не сдвинуть RNG-потоки других частей
кода, но do_rewire_event не вызывается, граф не меняется), v10_unit_
tests.py (3 теста, см. ниже), v10_pilot.py, v10_full_run.py,

**Метод -- Этап 1 (обучение M0):** 24 траектории (3 геометрии x 2
истории роста x 2 повтора x 2 порядка AB/BA), тот же протокол v0.8 (24с,
60 последовательностей A->B/B->A, 48 отметок перестройки), те же
исходные сети/группы/воздействия/электрические шумы. Единственное
отличие от M1/M2 -- политика перестройки "none".

**Метод -- Этап 2 (функциональная проверка):** 144 пары (24 обученных

**Метод -- Этап 3 (сравнение с v0.9):** ΔD_weakest = D_M1 - D_M0,

1. rewire_policy="none" никогда не меняет граф (проверено на прогоне,

- "15 нулевых из 24" для ΔD_weakest означает, что в большинстве

**Допустимый вывод (финальная формулировка v0.10):** "Добавление

структурных различий или их бесполезности; это означает, что в данной

  полезности следа порядка. Это дефект спецификации меры, обнаруженный

**Допустимый вывод:** заранее объявленное правило чтения (вывод о
полезности допустим только при согласии не менее 2 из 3 мер при

просмотра результатов.

по знаку на всех проверенных уровнях и переживает исправленный
перестановочный тест -- это самое сильное направленное функциональное
наблюдение за всю линию v0.8-v0.11 (в v0.9/v0.10 знаковых эффектов не
находилось вовсе). Но оно остаётся ОДНОЙ мерой, его среднее не
превышает разброс между комбинациями, и по правилу проекта одна мера --
наблюдение, а не вывод.

остальной сети.

**Критическое ограничение конструкции (осознано по итогам, не обойдено).**
Чтобы исключить артефакт стимуляции, из признаков убраны узлы групп A
и B. Но выученный след живёт ИМЕННО в контактах и весах между A и B --
то есть исключение артефакта убрало и те узлы, где след действует.
Поэтому вывод строго означает: порядок не доходит до ОСТАЛЬНОЙ сети.
Он НЕ означает, что след не имеет функционального эффекта внутри
A/B. Прямое считывание с A/B при этом невозможно чисто: в порядке AB
группа B принудительно активируется на 60мс, в порядке BA -- на 50мс,
и её рефрактерность/адаптация тривиально различаются на 10мс
независимо от какого-либо следа. Эта проба в принципе не может чисто
проверить информацию о порядке в группах, которые сами стимулируются.
Требуется другая конструкция (например, предъявление ТОЛЬКО первой
группы и считывание со второй -- это уже сделано в U1 фазы 1), а не
доработка этой.

## v0.11 (фаза 3): причина U1/U3 найдена и проверена вмешательством

**Вопрос:** гипотеза "быстрее, но менее устойчиво" (U1 против U3) --
единый компромисс от одного механизма или два разных явления,
случайно совпавших по знаку? На данных фаз 1-2 непроверяемо: U1 и U3
там были двумя поведенческими статистиками с одних и тех же проб.

**Файлы:** v11_mechanism.py, v11_intervention.py, v11_intervention2.py,
v11_intervention3.py, v11_mechanism_dW.npy, v11_intervention*.npz.

### Шаг 1. Структурная причина (на сохранённых данных обучения)

`dW` -- суммарный вес связей ИСТОЧНИК->ЦЕЛЬ в выученном направлении,
перекрёстная форма (как U1 и структурный C в v0.8):
- полный блок: среднее **+0.0726**, знак положителен на **36 из 36**
  комбинаций, ни одного отрицательного;
- только веса (по контактам, общим для обеих ветвей): **+0.0548**,
  36/36 положительных;
- вклад топологии: **+0.0178**, 25 положительных, 11 нулей, 0
  отрицательных.
Знак одинаков на всех 3 парах групп и всех 3 геометриях. Топология
блока A-B совпадала между ветвями лишь в 11 из 36 комбинаций.

Корреляции: corr(dW, U1)=+0.70, corr(dW, U3)=-0.47, corr(U1,U3)=-0.53.
Все три посчитаны на одних данных и причинности НЕ устанавливают --
поэтому шаги 2-4.

### Шаг 2-3. Причинная проверка вмешательством

Метод (в традиции контролей v0.1, transmission=False): несовпадающей
по порядку ветви ПЕРЕСАЖИВАЕТСЯ блок весов совпадающей ветви. Свежие
тестовые шумы 980-1019, цензурирование 0 из 14400 проб.

Латентность (мс, меньше = быстрее), 72 ячейки:
```
mis        -0.2267     несовпадающая ветвь как есть
ctrl_rand  -0.2264     контроль специфичности: блок W[цель, R],
                       R -- 5 случайных узлов вне A и B
tw         -1.1705     веса выученного пути, только общие контакты
tf         -1.4767     веса + топология
match      -1.4250     совпадающая ветвь
```
Разрыв mis-match = **+1.1983 мс** -- это U1, воспроизведённый на
НЕЗАВИСИМЫХ шумах. Доли разрыва: **tw +78.8%** (ускорил в 48/72
ячейках), **tf +104.3%**, **ctrl_rand -0.0%** (ускорил в 1/72).

**Отбракованный контроль и почему.** Первым контролем был блок
ОБРАТНОГО направления W[A,B]. Он дал ровно ноль, но при разборе
механики выяснилось, что этот ноль ГАРАНТИРОВАН ПО ПОСТРОЕНИЮ: блок
несёт сигнал от B к A, а измеряется время ПЕРВОГО импульса в B -- до
него B по определению не срабатывала и повлиять не могла. Любая
корректная реализация дала бы ноль. Контроль подтверждает исправность
кода, но специфичность пути НЕ проверяет, поэтому заменён на
ctrl_rand -- путь, который влиять МОЖЕТ. Обязательная проверка
"изменило ли вмешательство веса": tw 69/72, ctrl_rand 66/72, tf 72/72
(в 3 ячейках у tw не нашлось общих контактов с различающимися весами).

### Шаг 4. Тот же механизм -- и для надёжности

Разброс растра группы-цели (больше = менее надёжно), те же 72 ячейки:
```
mis       0.009615
ctrl_rand 0.009615
tw        0.009650
match     0.009667
```
Разрыв match-mis = **+0.000052**; **tw закрывает +67.4%**,
**ctrl_rand -0.5%**.

**Допустимый вывод:** гипотеза "быстрее, но менее устойчиво"
ПОДТВЕРЖДЕНА как единый компромисс: ОДИН и тот же блок весов
источник->цель причинно сдвигает ОБЕ меры, а равноценное вмешательство
на другом пути не сдвигает ни одну. Механизм: STDP усиливает выученное
направление (dW>0 на 36/36), усиленный путь ускоряет отклик и
одновременно делает его менее воспроизводимым.

Это частично закрывает вопрос, открытый с v0.9 ("вклад весов и вклад
топологии не разделены"): по латентности веса дают 78.8%, добавление
топологии -- остальное (tf 104.3%).

**Ограничения:**
- **Величина эффекта по надёжности ничтожна:** 0.009615 -> 0.009667,
  относительное изменение ~0.5%. "Закрывает 67.4%" -- это 67.4% ОТ
  КРОШЕЧНОГО разрыва. Направление устойчиво и причинно приписано, но
  практическая значимость НЕ установлена. Напомним: в фазе 1 U3
  составлял 0.64 от собственного разброса между комбинациями.
- tw ускорил в 48 ячейках из 72, то есть по отдельным ячейкам эффект
  заметно шумнее, чем по среднему.
- **Ускорение отклика -- НЕ полезность.** U1 измеряет скорость, а не
  качество решения какой-либо задачи. Заранее объявленное правило
  (согласие >=2 мер из 3) по-прежнему НЕ выполнено, вывод фаз 1-2
  "полезность НЕ установлена" НЕ меняется.
- Вмешательство меняет сеть искусственно (гибрид двух ветвей); оно
  устанавливает причинную достаточность блока для сдвига мер, но не
  утверждает, что в естественной динамике работает только он.
- 72 ячейки = 36 связанных комбинаций x 2 направления, НЕ независимые
  наблюдения.
